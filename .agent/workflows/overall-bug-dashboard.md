# Overall Bug Dashboard Workflow

> **Purpose**: Generate a single-view dashboard aggregating bug data across ALL modules, with live GitHub Issue status and developer attribution.
> **When to use**: Management reporting, sprint reviews, weekly standups, or anytime you need "where does the entire project stand?"
> **Differs from**: `/sprint-status` (sprint-level only), `/system-health` (risk heatmap, no developer attribution)

## Prerequisites
- At least 1 module audited via `/module-bug-audit`
- GitHub tracking set up via `/github-bug-tracking`
- `.agent/config.md` exists with `{REPO_OWNER}` and `{REPO_NAME}`

## Steps

### Step 1: Load Config [Antigravity]
// turbo
Read `.agent/config.md` → extract `{REPO_OWNER}`, `{REPO_NAME}`, `{PROJECT_ROOT}`

### Step 2: Discover All Audited Modules [Antigravity]
// turbo
1. List all subdirectories in `bug_report_AI/` (each = one audited module)
2. For each module directory, check if `*CONSOLIDATED*` report exists
3. Build the module list:
   ```
   Modules found: Estimation, Billing, ... (N total)
   Modules with audit data: {list}
   Modules without audit data: {list}
   ```

### Step 3: Collect Local Bug Data [Antigravity]
// turbo
For each audited module:
1. Read `bug_report_AI/{module}/CONSOLIDATED_BUG_REPORT.md` (or equivalent)
2. Read `bug_report_AI/{module}/*_EXECUTION_PLAN.md`
3. Extract per bug:
   - Bug ID
   - Title
   - Severity (P0/P1/P2/P3)
   - Track (A/B)
   - Category
   - Sprint assignment
   - Local status (✅ Fixed / 🔧 In Progress / ⏳ Queue)
   - GitHub Issue number (if recorded: `GitHub: #{N}`)

4. Read `bug_report_AI/ACTIVE_BUGS.md` → get all in-progress/blocked bugs
5. Read `bug_report_AI/FIX_VELOCITY.md` → get timing data (if exists)

### Step 4: Pull Live GitHub Status [Antigravity]

> [!IMPORTANT]
> This step pulls LIVE data from GitHub. If GitHub is unreachable, fall back to local status from Step 3.

#### 4a. Get All Open Issues
Use platform dispatch → `List issues` (see `/github-bug-tracking`):
```
Owner: {ISSUE_OWNER} (from config — Gitea or GitHub)
Repo: {ISSUE_REPO}
State: OPEN
Per Page: 100
```

#### 4b. Get All Closed Issues
Use platform dispatch → `List issues` (see `/github-bug-tracking`):
```
Owner: {ISSUE_OWNER}
Repo: {ISSUE_REPO}
State: CLOSED
Per Page: 100
```

#### 4c. For Each Issue, Extract:
| Field | Source |
|---|---|
| Issue Number | `issue.number` |
| Status Label | `status:triaged`, `status:in-progress`, `status:testing`, `status:deploying` |
| Assignee | `issue.assignees[0].login` → **who is working on it** |
| Closed By | `issue.closed_by.login` → **who fixed it** (only for closed issues) |
| Closed At | `issue.closed_at` → **when it was fixed** |
| Labels | All labels → extract severity, track, category, module |
| Milestone | `issue.milestone.title` → sprint assignment |

#### 4d. Reconcile GitHub vs Local
For each bug with a GitHub Issue number:
- **GitHub says closed + local says fixed** → ✅ Consistent
- **GitHub says closed + local says in-progress** → ⚠️ Local stale — update local to fixed
- **GitHub says open + local says fixed** → ⚠️ GitHub stale — flag for GitHub update
- **No GitHub issue** → 📝 Local-only bug (not yet pushed to GitHub)

### Step 5: Build Developer Attribution Table [Antigravity]
// turbo
From the GitHub data collected in Step 4:
1. Group closed issues by `closed_by` (the person who fixed it)
2. For each developer:
   - Count total bugs fixed
   - Count by severity (P0/P1/P2/P3)
   - Count by track (A/B)
   - Calculate average fix time (if `FIX_VELOCITY.md` has data)
3. For open/in-progress issues, use `assignees` to show who is currently working on each

### Step 7: Save Report [Antigravity]
Save the generated report to:
```
bug_report_AI/DASHBOARD_REPORTS/bug_dashboard_{DATE}.md
```

Create the `DASHBOARD_REPORTS/` directory if it doesn't exist.

> [!TIP]
> Keep the last 10 dashboard reports for historical comparison. Older reports can be archived.

### Step 8: Present to User [Antigravity → Human]
Display the full dashboard report. Highlight:
1. Any P0 bugs still open (action required)
2. Any blocked bugs (need human decision)
3. Any data inconsistencies between local and GitHub
4. Velocity trend — is the team speeding up or slowing down?

## Differences from Other Reporting Workflows

| Feature | `/sprint-status` | `/system-health` | `/overall-bug-dashboard` |
|---|---|---|---|
| Sprint-level progress | ✅ | ❌ | ✅ |
| Module risk heatmap | ❌ | ✅ | ✅ |
| Developer attribution | ❌ | ❌ | ✅ |
| Live GitHub status | ✅ (issues only) | ❌ | ✅ (full reconcile) |
| Fix velocity trends | Basic | ❌ | ✅ (weekly/all-time) |
| Data inconsistency check | ❌ | ❌ | ✅ |
| Recently fixed list | ❌ | ❌ | ✅ (with who fixed it) |
| Blocked bugs detail | ✅ | ❌ | ✅ (with days blocked) |
| Unaudited modules | ❌ | ✅ | ✅ |
| Saved as report file | Optional | ✅ | ✅ (with history) |
