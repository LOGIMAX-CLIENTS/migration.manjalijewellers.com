## Root Cause Analysis: Why 6 view_file After Discover?

### What discover provided (v3.6.0)

✅ `get_cash_book_opening()` full code (20 lines)
✅ `get_cash_book_opening_OLD()` commented code (50 lines)
✅ Controller `cash_book()` (40 lines)
✅ RAG inline: `branch_has_cash_opening()` (14 lines)
✅ RAG inline: `get_cash_openings()` (14 lines)
✅ RAG inline: `cash_opening()` controller (20 lines)
✅ Call chain: `cash_book_details → get_cash_book_opening → get_cash_in_hand`
✅ Formulas: 3 SQL aggregates
✅ Magic values: 5 report_type codes
✅ Called_by: 2 callers for get_cash_book_opening

### What the agent STILL needed to read

| File | What agent looked for | Why discover didn't have it |
|---|---|---|
| `cash_flow_model.php` (L36-180) | `get_cash_in_hand()` implementation — the **actual SQL** that should include opening_master | **L2 code was truncated** — discover shows L1 model method but not the L2 method body |
| `ret_reports_model.php` (L32766+) | `get_cash_book_details()` — the parent function that calls opening | **Only call chain shown, not parent function body** |
| `opening_master_model.php` | Full model with all methods | RAG showed 3 methods inline, but agent wanted the **table schema** |
| `ret_reports.js` | JS AJAX call that sends POST data | **No JS in LCA index** — legitimate gap |
| `admin_ret_reports.php` | Controller beyond line 8956 | Discover showed lines 8917-8956 only |
| `admin_opening_master.php` | How opening is saved to opening_master table | RAG showed this inline but only 20 lines |

### Key Insight

> **Discover surfaces WHAT methods exist but not enough of the critical business logic INSIDE L2+ methods.**

The agent's investigation pattern is:
1. Read discover → understands the call chain ✅
2. Reads `cash_flow_model::get_cash_in_hand()` → needs to see if it queries `opening_master` table ❌ (not inline)
3. Reads `ret_reports_model::get_cash_book_details()` → needs to see how opening balance is calculated ❌ (not inline)

The **L2 model code** (methods called by L1) is the biggest gap. Discover shows L1 model code but the agent needs L2 to understand the actual SQL logic.

## Recommendations for v3.7.0

1. **Include L2 method bodies** — When L1 calls are resolved from level2 dict, also read the L2 method source code from the file and include it (cap at 30 lines per method)
2. **Include parent function body** — The function specified in the URL (e.g., `cash_book_details()`) should have its model body included, not just the controller snippet
3. **Increase RAG inline cap** — Bump from 20 to 40 lines for top 2 results to reduce truncation
4. **LCA reindex with JS** — Run `lca index` with JS files included to capture AJAX→PHP mappings
5. **Include class constants** — Grep for `CASH_BOOK_FROM_DATE`, `TABLE_NAME`, etc. in the target model file
